# Conformance status

`docs/CONFORMANCE_STATUS.json` is the machine-readable status source for `AKASHIC-CT-001` through `AKASHIC-CT-181`.

Current classification highlights:

- default schema2/3, cache, recovery, resource and failure-semantics obligations remain local component evidence; CT-110 adds the schema3 live-byte cache invariant;
- CT-088–109 are explicitly `implemented-local-scope-limited` evidence for the package-internal schema4 directory-head candidate; they do **not** make schema4 the default or authorize automatic migration;
- CT-111 is a separate four-point schema4 process-crash matrix and remains process-crash evidence only, never a power-loss claim;
- CT-112 is deliberately `partial-local`: both a schema3-capability control reader and an unmodified rebuild of annotated historical tag `0.1.0-alpha.5` reject committed schema4 with `unsupportedSchema`, and the tagged-source reader leaves `manifest.json` bytes unchanged; both controls are replayed by `scripts/verify-release-readiness.sh` under one campaign source identity. This is stronger downgrade evidence but still not qualification of the original distributed historical binary artifact, so it does not authorize automatic migration;
- CT-113–123 are `implemented-local-scope-limited` migration-maintenance evidence: retired schema3 sidecars and payload manifest xattrs can be validated and repaid by schema4 physical maintenance, malformed lookalikes fail closed, and payload-xattr cleanup failure is retryable without changing logical authority. These obligations do **not** make migration automatic; payload-xattr debt can scale with the live set and is intentionally kept out of normal reopen;
- CT-124 is a separate seven-point schema4 distinct-key checkpoint process-crash matrix; CT-125 covers recovery crashing again while it reconstructs the two empty current-generation heads after a committed checkpoint snapshot. Both remain `implemented-local-process-crash`, never power-loss evidence;
- CT-126–129 harden bootstrap root-loss detection: an established schema3 payload or schema4 directory-head state cannot be silently reclassified as a fresh store when `manifest.json` is missing; malformed Akashic head-family metadata fails closed, while a genuinely fresh root still supports schema3 initialization on media that explicitly reports directory xattrs unsupported;
- CT-130–132 extend schema4 root-snapshot integrity: newer physical head evidence blocks legacy-root reversion, and the unreleased `directoryHeadV2` profile requires a semantic SHA-256 corruption seal over the snapshot generation/profile/compact entries. The prior unsealed `directoryHeadV1` research profile is rejected; the seal is not keyed authentication;
- CT-133–141 are `implemented-local-scope-limited` verified-read concurrency evidence: blocking reads leave the store actor under hard worker/byte/pending bounds, stale carrier failures cannot quarantine newer authority, pending cancellation uses O(1) token lookup, and tombstone-heavy pending storage is bounded while production admission remains strict FIFO;
- CT-142–157 are `retired` schema5 V2 binary-base qualification obligations. Their package-only research implementation and tests were deliberately removed from the slim repository, while the obligation IDs and historical scope remain in the ledger. `retired` carries no current implementation claim or evidence path; public `FileBlobStore.open` remains V1-only.
- CT-158–167 are `retired` schema5 V3/baseBinaryV2 qualification obligations. Their former package-only profile, transition, checkpoint, compaction and fault-qualification surfaces are absent from the slim repository; the ledger preserves historical identity without claiming current implementation, default adoption, migration, physical-device behavior or power-loss durability.
- CT-168–174 are `implemented-local` schema3 recoverability-headroom evidence. Direct `blobs/` children, including tolerated physical cleanup debt and crash-visible transaction temporaries, share the bounded reopen scan budget; successful mutations reserve headroom before creation, metadata pressure can fall back to root checkpoints, successful unlink returns slots in O(1), and pre-authority syscall failures use a bounded failure-only recount so cleaned temporaries do not become phantom capacity debt. These local filesystem/fault-injection obligations do not claim power-loss behavior or arbitrary external-directory-mutation tolerance.
- CT-175–181 are `retired` segmented V3/V4 checkpoint-topology qualification obligations. The former checkpoint-preseal, compound-run/preseal and run-collapse research surfaces were deliberately removed; these entries retain historical scope only and carry no current implementation evidence or adoption claim.
- CT-016 now has implemented-local owner-mismatch evidence using a real different-owner regular descriptor; the current local run exercised the non-root path against a read-only root-owned regular system file, while the test also contains a compile-validated temporary-chown fallback for root runners but does not claim root-runtime qualification. The remaining partial-local obligations are CT-019 and CT-112. CT-022–026 are now `implemented-local-scope-limited`: Fovea emits a durable source-bound host receipt whose five semantic tests are pinned to Akashic `0.1.0-alpha.7`, and Akashic mirrors and validates that receipt. The receipt remains local host-composition evidence only; it does not imply protected-release or physical-device qualification.

The status uses several non-equivalent labels:

- `implemented-local`: named local evidence exists;
- `implemented-local-process-crash`: actual child process termination and reopen evidence exists, but not power-loss evidence;
- `implemented-local-cross-process-lock`: kernel lock behavior was observed through another process;
- `implemented-local-scope-limited`: the stated narrow scope is tested and broader semantics are explicitly unsupported;
- `partial-*`: useful evidence exists but the obligation is not closed;
- `planned`: no implementation claim for work that remains prospective;
- `retired`: historical obligation identity is retained after its research implementation/test surface is deliberately removed; it carries no current evidence path or implementation claim.

Component evidence cannot close Fovea host obligations. Passing Akashic Disk tests alone does not prove ContentID projection, HTTP record transaction, namespace revocation or final delivery degradation inside Fovea. Fovea now owns and emits a source-bound semantic receipt for CT-022–026. Akashic keeps a durable mirror and validates the exact host/component identity, obligation set, source hashes and alpha.7 revision. A real Git checkout additionally resolves the annotated alpha.7 tag to the receipt revision; a Git-free source-identity clean copy validates the explicit tag/revision formats and package-resolved binding without pretending that repository refs were copied. When a Fovea checkout is available, the verifier additionally recomputes the live Fovea working-tree identity and source hashes. This closes only the listed host-composition semantics, not release or physical-device qualification.

The status rules keep `candidateDoesNotImplyDefault=true`, `directoryHeadCandidateDoesNotImplyAutomaticMigration=true`, and `snapshotCorruptionSealDoesNotImplyAuthenticatedStorage=true`: implemented local evidence for an opt-in candidate does not make it the Fovea default, authorize automatic migration, or turn an unkeyed corruption seal into an authenticated-storage claim.
